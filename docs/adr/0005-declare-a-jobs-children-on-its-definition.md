# Declare a job's children on its definition, not at the call site

A job that waits on others declares them on its definition, under `awaits`, one named slot per job it waits on. The shape of a slot declares its arity: a bare definition is exactly one child, and an array holding one definition is many of them. `jobs.enqueue` then takes what fills every slot as its third argument, and the handler reads what they returned under the same slot names.

The parent's contract used to be spread over three files that nothing kept in sync: the definition said what the job was, a `jobs.flow` call said what it waited on, and the handler asked `context.children(definition)` for whatever it hoped had been passed. A flow enqueued one child short compiled, ran, and gave the handler a short array. Now the definition is the single source: the enqueue input and the handler's `children` are both derived from `awaits`, so the three cannot disagree.

The slot, not the definition, became the name of a child. Two slots can hold the same definition — `previous` and `current`, both running the same fetch — and a child named after its definition could not tell them apart. So a child's stored id changed from `<definition name>~<uuid>` to `<slot>~<uuid>`. This is what let the flow read shrink to the two hashes BullMQ already keeps on the parent: the slot travels in the key, and the parent knows slot to definition from its own `awaits`. The `HGET name` round trip per child and the `childName` fallback for ids written before the marker existed are both gone, not replaced.

The dispatch reads the children from the definition, not from `envelope.origin`. The origin is written once, at the enqueue that produced the job, and it is a fact about that enqueue; `awaits` is a fact about the definition the delivery runs against today. Gating the read on `origin === "flow"` let three jobs run over empty slots and complete green: one enqueued by a schedule, one written by a build where the job waited on nothing, and one whose children were all cancelled. The definition is the only source that is right at dispatch time, so it is the gate. A definition that waits on nothing costs no round trip, which is every ordinary job.

## Consequences

`unique`, `idempotencyKey` and `schedule` are now refused at `defineJob`, on any definition that declares slots, rather than at the enqueue that made a flow. Waiting on children is a property of the definition, so the refusal belongs where the definition is written. `schedule` is the one this decision added: a recurrence enqueues one job on its own, with no producer to pass what fills its slots, so the pair has no run that could be correct. The `schedule` goes to a job that waits on nothing, and that job's handler enqueues the flow. `unique` is still refused again while composing the tree, because a definition that declares no `awaits` is an ordinary job on its own and only becomes part of a flow by filling somebody's slot.

Every node of a flow carries how many children each of its slots was given. Redis cannot answer that question: the only write is one member per child in the parent's `:dependencies`, and a child that is cancelled or removed is taken out of that set with nothing left behind, so a slot that lost a child is byte for byte a slot enqueued smaller. The composition is the one moment the declared shape is known, so it is written into the envelope, one count per slot — including `0` for a slot declared as many and filled with an empty array. A count, not a value, is what is compared: a child whose handler returned nothing is stored as `"null"`, so a slot full of void children reads exactly like an empty one.

The absence of that record is read as a fact too — the job was enqueued by a build where it waited on nothing — and it carries the same burial, `children_short`, with a different message and a different repair. Neither case is retryable: the missing child is gone, and the fix is to enqueue the flow again from the top. A `child_dead` burial stayed separate for that reason, since retrying the named child puts that flow back together.

A child still in flight is the one refusal that is not a burial. A parent can reach its dispatch beside a child that was retried behind it, so that attempt fails retryably before the handler and the next one reads a full set. Redis refuses the completion of such an attempt anyway; failing early only moves the refusal ahead of the handler's side effects.

A slot name cannot hold `:` or `~`. The child's id is built from it, and both characters are read as structure — the first cuts a job id into queue and stored id, the second cuts a child id into slot and uuid.

The types stop speaking wherever a `JobDefinition` is widened to its default type parameters: that erases `Awaits`, and the third argument of `enqueue` becomes optional at the type level. A run-time assertion in `enqueue` reads the definition alone and refuses an enqueue that is short or whose arity disagrees. It looks redundant beside the types and is not.

Three type errors are worse than the rule behind them, and are documented in the README rather than fixed. An enqueue input built in a `const` before the call is checked as a whole afterwards, so the leaf error collapses into a wall as deep as the tree; annotating that `const` with `AwaitsInput<typeof definition>` restores it. A slot written `[a, b]` reports `not assignable to type 'undefined'`, which says nothing about one definition per slot. A parent slot filled with a flat payload instead of `{ data, awaits }` reports a field of that payload missing from the wrapper, which names the symptom and not the rule.
